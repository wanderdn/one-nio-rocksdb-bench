## Что установил эксперимент и как читать результаты

Цель этой серии — исследовать случайные чтения при **очень малом общем бюджете ресурсов: один разрешенный логический CPU, 1 ГиБ RAM на весь контейнер и датасет 4 ГиБ**. Это одна измеренная конфигурация под жестким ограничением памяти, а не определение максимальной производительности one-nio, RocksDB или NVMe.

В равноресурсной серии MultiGet с io_uring показал 45 706 GET/с, one-nio — 4 959 GET/с, одиночный RocksDB Get **без io_uring** — 5 899 GET/с, MultiGet без io_uring — 6 420 GET/с. Следовательно, именно MultiGet с io_uring опередил эти три варианта по throughput в 9,22, 7,75 и 7,12 раза соответственно. Обычный Get без io_uring опередил one-nio примерно на 19%; утверждения о семикратном преимуществе обычного Get здесь нет.

**Один поток клиента не равен одному I/O в полете.** Одиночные Get в этом harness выполняются последовательно: вызов, ожидание результата, следующий вызов. MultiGet передает 5 000 ключей одним вызовом, а backend с io_uring может отправить несколько независимых чтений до ожидания их завершения. Поэтому измеряется и преимущество пакетной организации дискового I/O, а не только стоимость поиска ключа внутри движка.

Для последовательного одиночного Get замена pread на отправку одного запроса через ring с немедленным ожиданием сама по себе не создает перекрытия запросов. Штатный Java RocksDB.get() в этой сборке использует pread с Direct I/O. Проверка async_io=true не обнаружила io_uring_enter; создание rings не означает чтение через них. См. [проверку Get](GET-IO-URING.md). Полноценный тест отдельного GetAsync или другого файлового backend не проводился и не включен в таблицы.

Низкий процент CPU сам по себе не означает наличие резерва пропускной способности: последовательный клиент может ждать завершения I/O. Для интерпретации нужны совместно wall time, CPU time, cache misses и счетчики I/O. Major page faults mmap и явные Direct I/O чтения RocksDB — разные механизмы учета; ноль major faults у RocksDB не означает чтение из RAM.

Все основные и дополнительные измерительные профили выполнены по 5 млн GET после 1 млн warmup GET, с одинаковым полным лимитом памяти и CPU. Полезный кеш, занимаемая RAM и внутренние структуры движков при этом могут различаться. Дополнительная серия без кешей данных описана в [NOCACHE.md](NOCACHE.md): результаты с кешами и без них получены в разные сессии Docker, поэтому небольшой выигрыш одной серии над другой не доказывает общий вред кеширования.

Один полный прогон на конфигурацию, WSL2/VHDX и фоновая нагрузка ограничивают переносимость выводов. Ни насыщение всех ресурсов, ни глобальный оптимум настроек, ни предел масштабирования этим экспериментом не установлены. Следующий этап — отдельная матрица CPU, общего RAM, потоков/конкурентных запросов и запросов в полете с повторениями, сменой порядка запусков и доверительными интервалами. Эти будущие тесты пока не выполнены.

**Что означает CPU №2:** это индекс одного логического процессора в нумерации ОС с нуля, а не два ядра. Параметр --cpuset-cpus=2 ограничивает affinity всего контейнера единственным логическим CPU с индексом 2. Физическое ядро при SMT может иметь другой логический поток, доступный остальным процессам хоста; эксклюзивное резервирование целого физического ядра этим параметром не обеспечивается.
